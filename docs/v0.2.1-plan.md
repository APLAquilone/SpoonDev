# v0.2.1 計画 — 収集・リスナー指標・画面構成

作成日: 2026-10-09。現状確認の基準: v0.2.0 / `9742491`。
この文書は実装計画であり、本番への適用や収集プロセスの起動を意味しない。
実装と検証はDevで行い、レビュー後に既存の本番更新手順で公開する。

## 1. 到達点

- 配信者を設定すると、必要な月間温度・DJ別Spoonの収集対象に自動で加わる。
- ダッシュボード、検索詳細、お気に入り、ファン一覧が同じ取得済みデータと指標を使う。
- 自枠だけの平均温度に代わり、複数DJで観測された行動を示す「滞在指数」を提供する。
- Spoon総数だけで判断せず、応援先の広がり・集中と自枠への実績を示す「投げ指数」を提供する。
- 左側は日常の操作、右上はアカウント・管理・説明ページの入口として整理する。
- 一般ユーザーの配信者紐付けを初回確定後にロックし、タグの管理を選択式にする。

指数は0〜100の参考値として設計する。確率、実際の滞在時間、将来の支援の保証にはしない。
材料不足は0点にしない。実装完了と、指数を算出できるだけの観測蓄積は別の条件とする。

## 2. 現在のDJ別Spoonが表示されない件

確認できた現在の仕様:

- `collect-spoon` は公開ライブのリスナー・温度、`collect-monthly` は当月ランキングを収集する。
- DJ別Spoonは別の `collect-gifts --dj-id ...` が必要。Web起動・プロフィール登録では起動しない。
- Spoonの表示先は自分のダッシュボードだけ。検索詳細・お気に入り・ファン一覧への表示は未実装。
- Spoonランキングの集計期間は未確認で、保存値も `source_period='unspecified'`。
- Devと本番は観測DBが別。別環境や別DJで収集した値は、自分のダッシュボードの値にはならない。

Mac本番で自DJについて取得する現在の手順（温度収集とは別ターミナル）:

```bash
conda activate spoondev
cd ~/SpoonDev
python -m spoondev collect-gifts --dj-id 316644201 --max-pages 0 --interval 3600
```

対象がしらたまもなかなら、`--dj-id` を `312029086` に替える。
カスタムDBでWebを起動している場合は、収集側にも同じ `--db` を指定する。
既に同じ対象のSpoon収集が動いていれば重複起動せず、そのプロセスとDBの更新状態を確認する。
Macの実際のDB・プロセスは未確認なので、今回の症状の原因を一つに断定しない。

v0.2.1では、未取得・取得待ち・部分取得・失敗・古い記録・数値0を区別する。
直前の正常なデータを、最新の失敗状態と併記できるようにする。
APIが数値0を返した場合だけ0として扱い、ランキングに見当たらない人を0にしない。

## 3. 収集を操作につなぐ

### 起動と対象

Webとは独立して動く収集workerをMacの通常起動手順に組み込む。
配信者の登録・既存設定の移行で対象を永続キューに追加する。
WebやTunnelの再読み込みのたびに収集workerを増やさない。
導入時は既存の手動収集との重複を確認し、利用者のDBを削除せず移行する。

優先順位:

1. ログインユーザーに紐付く自DJの月間温度・Spoon。
2. 自枠の最近のリスナーについて、取得済みライブ・月間温度から分かった出現先DJ。
3. お気に入り・登録ファンの既知の出現先DJ。
4. その他の既知DJの不足分。

非配信中の既知DJも月間・Spoonの対象にする。
対象は発見済みのDJであり、全Spoonユーザーや全訪問先を網羅した扱いにはしない。

### 更新と並列実行

- ライブは現行の約5分を基準に、枠の実際の取得間隔を記録する。
- 月間・Spoonは現行の約1時間を基準に、DJ単位の更新期限でスケジュールする。
- 自枠の観測を優先する。全体の頻度増加より、欠測・取得時間・更新の偏りの改善を先に行う。
- 独立したDJの取得は並列化し、同じDJ・取得種別のジョブは重複排除する。
- APIへのリクエスト間隔と429の待機期限をworker間で共有し、再起動後も待機を引き継ぐ。
- 予算内で処理できない対象は次回へ回す。「全件完了」と表示しない。
- 待機時間が長いジョブの優先度を上げ、低優先度の無期限待機を防ぐ。

現行CLIの `--interval` は1巡が終わった後の待機時間なので、更新間隔には巡回時間も加わる。
新workerでも期限どおりの取得を保証する表示にはせず、実際の取得日時を使う。
共有するのは公開観測のジョブとデータであり、どの利用者が誰を登録したかは公開しない。

### 必要な記録

取得回ID、枠ID、取得開始・終了、ページ数、取得完了状態、試行失敗・待機理由を保存する。
SpoonはDJ・リスナーごとに発見元、取得日時、期間の確認状態、数値の有無を保持する。
途中取得から安全に再開できる範囲を調査する。APIが再開できない場合は再取得と明示する。

## 4. 滞在指数

### 示すもの

「観測できた範囲で、同じ枠で続けて見つかり、別の日にも戻ってくる傾向」を示す。
温度の平均は滞在時間に換算しない。元の温度と月間温度は補足情報として残す。

評価要素:

- 同一枠の次の有効な取得でも見つかった割合。
- 同一枠で3回以上続けて観測された割合。
- 同じDJで複数の日に観測された割合。

自枠と他枠を含む全体の傾向、自枠での実績を分ける。
一人のDJや大量の同日取得だけで全体の指数が決まらないよう、DJ・日ごとの寄与を制限する。
暫定的な重み候補は継続観測50%、複数日の再観測30%、3回以上の連鎖20%。
実データの分布と取得間隔による偏りを確認してから採用を決める。

### 誤判定を避ける条件

- 同じ人が2回見つかっても、その間の離席・再入場は不明。連続滞在時間とは呼ばない。
- 同じDJでも枠IDが違えば、連続した同一枠の観測としてつながない。
- 途中取得で見当たらない、未取得、失敗、収集停止、枠の消失は「不明」。離脱扱いにしない。
- 全ページ取得でも、一覧取得中の入退場があるため厳密な同時点の在室判定にはしない。
- 長い観測間隔は連鎖を切る。停止中の時間を滞在に加算しない。
- 複数枠への同時出現はそのまま残し、排他的な移動順序を作らない。

暫定的な算出条件は有効な比較10組以上、観測3日以上。
複数枠での傾向として表示するには2DJ以上を必要とし、1DJだけならそのDJでの実績を表示する。
間隔が長すぎるデータは継続観測の計算から外す。間隔の閾値は保存データで検証する。
指数と別に観測日数・DJ数・比較数・最終更新を持ち、信頼度の低さを低得点に置き換えない。

## 5. 投げ指数

### 総額と応援傾向を分ける

目的は「自枠にも応援する傾向を考えるための材料」であり、全DJの単純平均・総額順にしない。
カードの主表示を「投げ指数（参考）」とし、内訳に次の情報を置く。

1. 応援先の広がり: Spoonを確認できたDJ数。
2. 応援の集中: 最大の支援先の割合、有効な支援先の数。
3. 応援の規模: 比較できる範囲のSpoon値。大口一人が尺度を支配しない変換を使う。
4. 自枠との関係: 自DJへの取得済みSpoon、自枠での複数日の観測実績。

例:

| 観測できた応援 | 新たなDJへの参考評価 | 自枠での扱い |
| --- | --- | --- |
| 他DJ一人への大きな支援 | 総数だけで高評価にしない | 自枠の実績がなければ材料不足も残す |
| 複数DJへの支援 | 横断して応援する材料になる | 自枠との関係は別に確認する |
| 自DJ一人に集中した支援 | 広がりは小さい | 自枠への実績を明示し、集中だけで低評価にしない |

金額を比較できる場合の集中度には `HHI = Σ(各DJの構成比²)`、有効支援先数には `1/HHI` を候補にする。
総額に対する対数変換と広がりを組み合わせた参考値を試すが、重みは実データ検証前に固定しない。
自枠の既往支援と他枠への広がりを別の内訳にし、単一の総額から自枠への予測を作らない。

### データの条件

- APIの集計期間を確認する作業を先に行う。未確認の値を月間・生涯・今週の投げ額とは呼ばない。
- 期間・取得時点が比較可能でない場合、金額で重み付けした集中度・合成点を出さない。
- その場合も取得済みのDJ別Spoonと、支援を確認できたDJ数は表示する。
- ランキング不在・額不明・未取得は0扱いにしない。取得済み1DJだけで「一人の推し型」と断定しない。
- 公開ランキング全ページの取得は、そのDJへの全支援者の把握を保証しない。
- 減少はリセット・補正・期間変更の可能性として記録し、再出現時に全額を新規支援へ加算しない。
- 正の差分も、期間が未確認ならランキング値の増分。実際の投げイベントとは断定しない。

暫定的な比較条件の候補は比較可能な3DJ以上、発見済みDJの80%以上で24時間以内の取得完了。
これは発見済み範囲の取得率であり、Spoon全体の網羅率ではない。
期間や比較範囲が確認できない場合、指数欄は「材料不足」とし、確認できた実績を表示する。
将来の「自枠に投げる確率」は、実際の投げイベントを取得し、時間順に検証できる段階で別に設計する。

## 6. 画面構成

```text
左ナビ                         右上: ログインユーザー名
├ ダッシュボード               ├ アカウント設定
└ リスナー検索                 ├ ユーザー管理（管理者のみ）
  ├ 検索                     ├ サービスについて
  ├ お気に入り               │ ├ 取得範囲・更新について
  └ ファン検索               │ ├ リリース履歴
                              │ ├ 利用規約
                              │ └ プライバシーについて
                              └ ログアウト
```

- スマホでもアカウント入口を最上部の右端に置く。ナビの展開で位置が下へ押されない構造にする。
- 検索・お気に入り・ファン検索はリスナー検索内の切り替えとして実装する。
- リスナーのカードと詳細は共通部品・共通データを使い、取得日時や指数の意味が食い違わないようにする。
- 月間温度・ライブ観測・Spoonを混ぜず、詳細で実測値と指標の根拠を確認できるようにする。
- 技術的な取得範囲はメイン画面から説明ページへ移す。
- メイン画面には未取得・材料不足・最終更新など、値を判断するための短い表示だけ残す。
- リリース履歴は実際に公開した変更を載せる。既存の `docs/releases.md` は公開運用手順として保持する。
- 利用規約・プライバシー文書は実態に合わせて整備する。未整備の文書に制定日や同意済み状態を作らない。

## 7. 配信者紐付けとタグ

### 一般ユーザーの初回登録

1. SpoonプロフィールURLまたは数値IDを入力する。
2. 公開プロフィールを取得し、名前・公開ID・数値IDを確認ダイアログに表示する。
3. 「確定後の変更は管理者への依頼が必要」と表示して確定する。
4. 以後は一般ユーザーによる再設定・解除を画面とAPIの両方で拒否する。

キャンセルやプロフィール取得失敗では保存しない。
同時に2画面から初回登録しても、未設定を条件とする更新で片方だけが確定する。
ダッシュボードの対象はサーバーがログインユーザーの設定から決め、別DJを指定して切り替えられないようにする。
一般ユーザーのファン取り込みは紐付けた自DJに制限する。ファン全削除で配信者紐付けは解除しない。
公開プロフィールの検索・出現先の参照は継続して提供する。

既存の紐付けはその値でロックし、パスワード・お気に入り・ファン設定を保持する。
管理者は明示的な修正操作で変更でき、対象・操作・日時を記録する。
この仕組みは登録変更を制限するもので、Spoon側の本人認証ではない。
本人確認の仕組みを作るまでは、同じDJへの複数ログインアカウントの紐付けを禁止しない。

### タグの選択

- 初期候補は「利用者」「管理者」「テスト」。管理者が候補を追加できる。
- ユーザー作成・編集は候補から選ぶ。既存の「保守」や独自ラベルは候補に移行して保持する。
- 表示タグとアクセス権限を別欄・別操作にする。「管理者」タグだけでは権限を付与しない。
- 管理コンソールでは実際の権限を明示する。管理者以外からの管理API操作は拒否する。
- 使用中のタグを削除してユーザーの設定を失わせない。候補の廃止を設計する場合は割当先を確認する。
- `kitomoya` の管理者権限と、現在 `kitomoya` のみに許可している全体の収集・集計閲覧を維持する。

## 8. 実装順と完了条件

### 第1段階: 収集とアカウントの基盤

並列作業: 収集キュー・更新状態、配信者紐付けロック・移行、UI部品と画面遷移。
共有するAPIの契約とデータ状態を先に決め、独立した作業を並列実装する。

完了条件:

- 登録済みDJが自動で収集対象になり、未取得の理由を確認できる。
- 再起動・429・部分取得で重複workerや誤った完了表示が発生しない。
- 一般ユーザーは直接APIでも自DJを変更・解除できない。
- 既存アカウント・観測DB・私有設定を失わず移行できる。

### 第2段階: 共通表示と指標

並列作業: 滞在指数、Spoonの比較条件調査と投げ指数、各一覧への共通表示。

完了条件:

- 同じリスナーについてダッシュボード・詳細・一覧の数値と更新日時が一致する。
- 未取得やランキング不在は0にならず、古い正常値と最新の取得状態を区別できる。
- 温度やSpoonの値を変えても滞在指数は変わらない。
- 欠測・収集停止・別枠・重複取得で滞在指数が誤って上がったり下がったりしない。
- 一推しへの高額支援だけで新たなDJへの評価が高くならない。
- 自枠が一推しの場合、その実績を集中度だけで低評価にしない。
- 未来の観測を使わず、計算時点までのデータだけで指標を算出する。

### 第3段階: 画面整理・Devレビュー

完了条件:

- 左側の入れ子ナビ、右上メニュー、初回確認ダイアログを320px・390px・PC幅で操作できる。
- キーボード操作、戻る操作、ポップアップのスクロール・閉じる操作を確認する。
- タグ変更で権限が変わらず、管理者のみユーザー管理を操作できる。
- 更新状態の詳細、公開済みの変更履歴、説明文書に右上から到達できる。
- 実データでしらたまもなかと自DJの取得・表示経路を確認する。
- 材料不足の利用者に架空の指数を出さない。

公開時はDBバックアップを取り、既存のリリース手順で更新する。
Tunnelを維持できる稼働構成ならURLを維持する。Macの稼働状態を確認せずURL維持を保証しない。
収集期間を要する指数は、公開直後から全員に数値が出るものとして案内しない。

## 9. 今回の対象外

Spoon本人認証、課金プラン、将来の支援確率の機械学習、総投げ額の円換算、全サービスの完全網羅。
これらを未実装のまま実装済みとして見せない。
