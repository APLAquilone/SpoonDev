# v0.3.0 Dev確認

ブランチは `dev/v0.3.0`、Macの開発画面は `http://localhost:8081` です。

## 活動時間の対象

ログインアカウントに紐付いた自分のSpoon数値IDから、次の人を対象として選びます。

- 自分が登録したファン
- 日本時間の今月、自分の枠でリスナーとして観測した人
- 自分の今月の最新取得ランキングで正の月間温度が確認できた人

対象者の活動時間には、保存済みの**他の配信者の枠での観測**も含めます。自分が配信していない時間にも観測があればグラフに入ります。他アカウントの非公開ファン一覧は使いません。対象別に切り替え、7日／28日の「日付×時間帯」を確認できます。時間帯だけの別グラフは廃止しました。

時間帯は日本時間です。同じ日・同じ時間帯の同じ人は、複数の枠や何回の取得で見つかっても1人として数えます。期間全体の観測人数も重複を除きます。分類は現在の登録一覧・今月の記録を、表示期間の観測へ適用します。月が替わると今月の来訪者と月間温度の対象は変わります。

未観測はSpoonを開いていなかった証拠ではありません。収集できなかった枠、潜っている人、取得間隔の間の活動は確認できません。部分取得では見つかった範囲だけを数えます。実際の起動・終了時刻や、連続した滞在時間は算出しません。

ユーザー詳細の「出現時間」では、その人がリスナーとして観測された日時を同じ形式で表示します。配信者として枠を開いていた時間は含めません。詳細の「リスナー観測」には、最後に観測した区間の最初と最後の時刻を表示します。枠の変更、15分を超える観測間隔、完全取得での不在を区切りにし、実際の入室・退出時刻とは区別します。一覧プレビューは直近30分の観測点に限定し、詳細は過去の区間も確認できます。

## ファン検索

未設定の場合はファン検索で自分の名前・プロフィールID・数値IDを検索し、対象を確認して登録します。既にプロフィールを設定した一般利用者は、そのプロフィールから設定します。紐付け後の変更は管理者に依頼します。フォロワー一覧の取り込みは本人が保存した一覧または数値IDで行い、Spoonのログイン情報は保存しません。

一覧は、絞り込み後の全登録件を3分類の順で並べてからページ分割します。選んだ並び替えは各分類の中へ適用します。

| 分類 | 判定 |
| --- | --- |
| いま聴いているユーザー（目安） | 直近10分以内で、その配信者の最新取得に本人が含まれ、温度が確認できた |
| 最近聴いていたユーザー | 直近30分以内にリスナーとして観測され、上の条件は満たさない |
| 登録したファン | それ以前の記録のみ、または未観測 |

温度0は取得できた値として扱います。温度欠損や新しい取得での不在は「いま」の目安から下げます。部分取得で見つからない場合も聴取中とは断定しません。いずれも現在の視聴を保証するものではなく、30秒ごとの画面確認と実際の収集には時間差があります。

## 管理者のお知らせ

右上のアカウントメニューから「お知らせ管理」を開きます。日付・重要度（お知らせ／重要／緊急）・内容を作成し、編集・削除できます。未来の日付は予約表示になり、日本時間の当日から利用者に表示されます。

実際の権限が利用者のログインアカウントに共通のお知らせ欄を表示します。表示タグが「管理者」「テスト」でも、利用者ロールなら受信します。管理者ロールには管理画面を表示します。内容はプレーンテキストとして扱い、HTMLは実行しません。お知らせはログインDBへ保存し、Dev・本番は各環境で独立します。

## Devを更新する

起動中のDevをCtrl+Cで止めてから実行します。公開側のTunnelを止める必要はありません。

```bash
conda activate spoondev
cd ~/SpoonDev-dev
bash scripts/update-dev-mac.sh dev/v0.3.0 && bash scripts/start-dev-mac.sh
```

取得失敗・未保存のコード変更・履歴の分岐があれば停止します。Devの `origin` が本番フォルダでも、GitHubから指定ブランチを取得します。DevにはDev用のログインアカウントを使います。保存済みデータで確認でき、新しい観測用の別コマンドは不要です。

Devでも収集する場合だけ、公開側との重複巡回を考慮して明示します。

```bash
SPOONDEV_COLLECT=1 bash scripts/start-dev-mac.sh
```

## 収集の復旧とMac常駐

新しいランチャーは、収集だけを監視して異常終了後に5〜60秒の間隔で復旧します。429の待機期限は再起動後も保持します。一つの取得タスクの失敗で他の取得まで停止させず、継続的なDBエラー時は収集を止めて復旧を試みます。失敗・途中終了の記録は完全取得の空一覧として保存しません。

標準の取得間隔はリスナー観測300秒、月間温度・DJ別Spoon3600秒、同時実行4です。処理時間・リクエスト待機・公開APIの反映遅れによって実際の間隔は伸びます。自動収集にはAPIリクエストの共有ペース制御と、同じ観測DBの二重起動を防ぐOSロックがあります。

期限を迎えたリスナー巡回はランキングより先に実行します。同時実行数が2以上の場合は、ランキングが全実行枠を占めないよう、リスナー用に1枠を確保します。取得対象の探索は別スレッドで行い、1回30秒の予算を設けます。探索の失敗や一部アカウントのprivate DBの不具合で、公開枠のリスナー巡回を止めません。共有API待機は全取得へ適用されるため、429の間はリスナー巡回も待機します。

Webターミナルを閉じても収集を継続するには、**収集したい環境のフォルダ**でMac用サービスを明示的に導入します。Devに入れるとDevのDBへ収集します。本番へ反映後に本番で使う場合は `~/SpoonDev` で実行してください。

```bash
python scripts/collector-service-mac.py install
python scripts/collector-service-mac.py status
```

古い `collect-spoon`・`collect-monthly`・`collect-gifts` は各ターミナルでCtrl+Cにより止めてから切り替えます。同じDBの既存自動収集は終了するまで保持し、新サービスがロックの解放を待ちます。他のプロセスを勝手に終了しません。

サービスはそのフォルダとPython環境の絶対パスを記録し、Macへのログイン後に起動します。フォルダの移動やConda環境の削除後は再導入してください。スリープ中・ネットワーク切断中・ログイン前は収集できません。WebやTunnelはこのサービスに含まれません。

サービスのログは `data/collector-service.log`、通常ランチャーのログは `data/collector.log` です。停止・解除は同じフォルダから実行します。

```bash
python scripts/collector-service-mac.py remove
```

既に公開中の旧ランチャーはWebのHUP更新だけでは監視方式が切り替わりません。収集サービスの導入はTunnelを再起動せずにできます。Quick Tunnelの停止・新規起動はURLが変わるため、公開側のWeb更新は従来の [リリース手順](releases.md) を使います。

### 既存の自動収集へ修正を反映する

コード更新だけでは、起動中のPython収集プロセスには修正が反映されません。まずDevを更新して本番へリリースします。公開ターミナルはそのままにして、別ターミナルで実行してください。

```bash
conda activate spoondev
cd ~/SpoonDev-dev
bash scripts/update-dev-mac.sh dev/v0.3.0 && bash scripts/release-mac.sh
cd ~/SpoonDev
python scripts/stop-collector-mac.py
```

最後のコマンドは読み取りだけで、停止しません。DBの所有者、実際のコマンド・起動時刻・作業フォルダ・OSロックを照合し、最新のリスナー観測時刻と直近30分の観測件数を表示します。heartbeatが新しくても、観測時刻が進まなければ取得の進行は確認できません。

表示された収集PIDを指定して、収集だけを終了してサービスへ引き継ぎます。以下は今回の診断で確認したPID `46651` の例です。PIDが変わっていれば停止せず、再確認してください。

```bash
python scripts/stop-collector-mac.py --stop --pid 46651 &&
python scripts/collector-service-mac.py install
```

停止前に所有情報を再照合し、対象プロセスの終了とOSロックの解放を待ちます。照合失敗や待機時間切れでは、強制終了や次のサービス導入を行いません。Web・Tunnel・別環境の収集・手動収集にはシグナルを送りません。停止後のサービス導入が失敗した場合は、そのエラーを解消してから導入コマンドを再実行します。

新しい観測が保存されたら、読み取りコマンドを再実行して観測時刻が進んでいることを確認してください。巡回中も枠ごとに保存するため、ファン一覧は対象者が見つかったところから更新されます。画面は30秒ごとに確認しますが、全巡回の完了時刻や全ファンの観測は保証しません。

### サービスがrunningでもDBを開けない場合

Macで `unable to open database file` が続く場合は、プロセスだけが起動し、収集が進んでいない可能性があります。今回の障害では収集PID `56770` が開いているファイル256個のうち250個がSQLite関連で、Macサービスの上限256個を使い切っていました。SQLiteのトランザクション用context managerはcommit／rollbackだけを行い、接続を閉じません。修正版では収集のポーリング・API予算・実行記録・ランキング読取り・復旧処理の接続を必ず閉じます。

既に上限に達したプロセスにはコード更新だけでは反映できません。この本番フォルダのnativeサービスが登録済みと確認できた場合は、コードを適用した後、同じサービスだけを再導入します。公開ターミナル・Tunnelはそのままにしてください。

```bash
conda activate spoondev &&
cd ~/SpoonDev-dev &&
bash scripts/update-dev-mac.sh dev/v0.3.0 &&
bash scripts/release-mac.sh &&
cd ~/SpoonDev &&
python scripts/collector-service-mac.py install
```

再導入は同じフォルダに由来するlaunchdサービスだけを更新します。この障害ではworkerがOSロックを解放していて停止補助の照合条件を満たさない場合があるため、古いPIDの停止コマンドを繰り返さないでください。再導入後は数分待ち、`python scripts/stop-collector-mac.py` の `last_listener_observation` が進んでいることを確認します。次回の巡回でも更新が続くことが確認できるまで、サービスのrunning表示や新しいheartbeatだけで復旧完了としません。

特定ユーザーの最終観測時刻は、その人が再度見つかった場合に更新されます。全体の取得停止とは区別して確認してください。

## 検証結果

- Python全336テスト成功（2026-10-10のDB接続解放修正後、実際のシンボリックリンクをTMPDIRへ設定）。認証・アカウントごとの集計範囲・最新取得の温度欠損・分類後のページ分割・収集の例外復旧・リスナーの優先実行・探索の期限と停止・所有プロセスの停止・待機期限の保持を確認しました。低いファイル上限・GC停止下で、ポーリングと再試行1,000回、実workerの収集・保存・停止128回も確認しました。
- 認証付きHTTPサーバーを使ったブラウザ確認160項目が320／390／1365pxで成功。個人グラフ、別枠の活動、ファン設定、お知らせの作成／編集／削除／予約、保存失敗時の入力保持を確認しました。JavaScriptエラー・ページの横はみ出しはありません。
- 同じ固定データ（5,040観測・252,000リスナー記録・対象50人）で、ファン一覧は約4.15秒から0.22秒、お気に入りは約4.01秒から0.21秒へ短縮しました。詳細の全履歴区間は維持します。これはクラウドでの比較で、Macの実運用時間はデータ量と環境に依存します。
- 配布wheelにグラフ・お知らせのJavaScript、CSS、新しい保存・収集監視モジュールが含まれることを確認しました。

Macのlaunchdによる実常駐と、利用者のMac上の現在の収集状態はこのLinux環境からは確認できません。公開APIのディレクトリ・月間温度・DJ別Spoon・リスナー一覧は少量の実取得で応答と形式を照合しました。
